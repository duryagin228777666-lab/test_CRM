# Журнал решений

Короткие записи по ходу работы: что решили, почему и что отбросили. Из этого собирается разбор.

## 2026-10-02

**Разбор задания и план.** Отдал ТЗ ИИ-агенту (Cursor, режим Plan). Сначала попросил задать уточняющие вопросы, потом написать план-промпт для себя. Вопросы были про стек, хостинг, пункт 2, доступ к CRM, нишу агентства и способ тегирования. Ответы зафиксированы в плане, дальше агент работал по нему в режиме Agent.

**Ниша: рекламное агентство (лидогенерация для бизнеса).** От ниши зависят вопросы бота и теги по умолчанию: таргет, контекст, seo, smm, сайт, консультация. Абстрактная CRM «для агентства» дала бы абстрактные теги.

**Стек: Python, FastAPI, aiogram 3, SQLite, серверные шаблоны Jinja2.** Это стек, на котором я быстрее всего довожу вещь до прода. SPA для пяти экранов была бы лишним весом: формы с POST и редиректом работают без сборки и без API-слоя. Отброшены Next.js и Supabase: больше движущихся частей при той же функциональности.

**Один процесс: веб и бот вместе.** Бот работает через long polling внутри lifespan FastAPI. Не нужен публичный webhook, отдельный воркер и очередь. Цена: можно запускать только один экземпляр, иначе Telegram отдаёт конфликт getUpdates. Для MVP это нормально.

**Один слой `leads.py` для всех источников.** Бот, личный Telegram и ручная форма создают лид одной функцией `create_lead`. Тег источника (`бот`, `личный tg`, `вручную`) ставится там же, его нельзя забыть в одном из входов.

**Теги — отдельная таблица и связь многие-ко-многим, имена в нижнем регистре.** Иначе «SEO», «seo» и «#seo» были бы тремя тегами. Тег, с которого сняли последнего лида, удаляется, чтобы не засорять фильтры.

**Автотеги плюс ручные.** Источник и услуга, выбранная кнопкой в боте, проставляются сами. Это даёт осмысленный фильтр «по тегу» с первой же заявки. Менеджер может добавить любые свои теги («горячий», «vip»).

**Поиск по кириллице.** В SQLite `LOWER()` не работает с кириллицей, поэтому зарегистрировал Python-функцию `py_lower` и ищу через неё. Поймал это тестом «поиск "петров" находит "Петров"».

**Найденный баг: `.env` из родительской папки.** `load_dotenv()` без пути ищет `.env` вверх по дереву и подхватил токен бота из соседнего проекта. Исправил явным путём к `.env` проекта.

**Анкета в боте: услуга, имя, контакт, задача, подтверждение.** Услугу спрашиваю первой: это самый простой вопрос (кнопка), и он сразу даёт тег. Имя предзаполнено из профиля. Контакт можно отдать кнопкой «Поделиться номером» или как @username. Перед отправкой показываю сводку, чтобы не было мусорных заявок. Сообщения, присланные после заявки, прикрепляются к лиду как переписка и пересылаются менеджеру.

**Дубли по одному пользователю не склеиваю.** Повторная заявка через /start даёт новый лид. Это осознанное упрощение: склейка требует правил (по телефону? по tg id? за какой период?), а это уже продуктовое решение.

**Доступ: один логин и пароль из env, сессия в подписанной cookie.** Ролей и команды нет, это за скобками MVP. Защита от CSRF держится на SameSite=Lax у cookie сессии.

**Пункт 2 через Telegram Business.** Бот подключается к личному аккаунту в настройках Telegram, и Bot API присылает `business_message`. Вариант с юзерботом на Telethon отброшен: пришлось бы хранить на сервере сессию личного аккаунта (по сути полный доступ к нему), а ещё это серая зона правил Telegram. Новый собеседник становится лидом с тегом `личный tg`. Дальнейшие сообщения в обе стороны ложатся в переписку. Если первым написал сам менеджер, лид не создаётся.

**Пункт 2, поворот: Telethon вместо Business.** Premium на аккаунте нет, а Business без него недоступен. Поэтому основным путём стал юзербот на Telethon (`app/personal_tg.py`), запущенный в том же процессе и event loop, что веб и бот. Вход выполняется один раз скриптом `python -m app.tg_login`, а строка сессии хранится только в секретах. Business-обработчики оставил: при появлении Premium их включает одна галочка в настройках Telegram, кода менять не нужно. Оба пути вызывают одну функцию `record_personal_message`, поэтому правила одинаковые:
- новый лид появляется только от входящего сообщения;
- если первым написал менеджер, лида нет;
- ответы менеджера ложатся в переписку лида.

У юзербота добавлен фильтр: люди из записной книжки не становятся лидами (`TG_SKIP_CONTACTS`), иначе каждое сообщение от знакомого попадало бы в CRM. Ещё игнорируются боты и служебный аккаунт Telegram с кодами входа.

**Проект вынесен из папки другого проекта** в отдельную `Desktop\test-crm`, со своим git и venv.

**Тесты.** Пять pytest-тестов на TestClient: вход, ручной лид, теги, фильтр, поиск, статусы, автотеги бота, правила личного Telegram. Объём кода не оценивают, но тесты дешевле, чем каждый раз прокликивать сценарий руками.
